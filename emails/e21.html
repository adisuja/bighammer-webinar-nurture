Both runs succeeded and the data didn't match. Here's the checklist that catches it, in the order we run it.

The five checks

1.Row and column counts. The fastest signal that something is off.
2.Schema. Same columns, same types.
3.Null rates per column. Catches silent handling changes.
4.Numeric aggregates. Sums, minimums and maximums on key measures.
5.Row-level comparison. By business key, or by hash when there's no clean key.
-- rows in the original output that the migrated output doesn't have
SELECT order_id, customer_id, ROUND(amount, 2) AS amount, order_date
FROM original.orders_daily
EXCEPT ALL
SELECT order_id, customer_id, ROUND(amount, 2) AS amount, order_date
FROM migrated.orders_daily

List the columns explicitly (set operations match by position), round floating-point measures to the tolerance you agreed, and run it both ways round. Zero rows in both directions is parity at row level.

What good looks like

Run the old and new jobs side by side on cloned data, so production is never touched.
Agree the checks and tolerances with the business owner before the migration starts.
Cut over in small groups of jobs, not all at once.
Keep the comparison results as evidence for sign-off.
