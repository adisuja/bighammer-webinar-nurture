A nightly job fails at 3 AM. Someone re-runs it. It times out. The third run succeeds, the incident closes, and everyone moves on.

The compute from the first two runs is still on the bill.

Why failure cost stays invisible

Failed, timed-out and retried runs consume compute until they stop. A job with no timeout can run for hours before it gives up. A job with generous retries can repeat that several times in one night.

Reliability tooling tracks the failure. It almost never tracks the cost of the failure. So the number that matters to finance never reaches the people who could fix it.

The most defensible number you have

Failed-run cost is unusual: it needs no assumptions about what might be saved. The runs happened, they failed, and they were billed. Measured runs, priced at list: that's the most defensible number you can put in front of a CFO.

WITH runs AS (
  SELECT workspace_id, job_id, run_id,
         MAX_BY(result_state, period_end_time)
           FILTER (WHERE result_state IS NOT NULL) AS final_state
  FROM system.lakeflow.job_run_timeline
  WHERE period_start_time >= current_date() - INTERVAL 90 DAYS
  GROUP BY ALL
), failed AS (
  SELECT * FROM runs WHERE final_state IN ('FAILED', 'TIMED_OUT', 'ERROR')
)
SELECT f.workspace_id, f.job_id, COUNT(DISTINCT f.run_id) AS failed_runs,
       SUM(u.usage_quantity * p.pricing.effective_list.default) AS failed_cost
FROM failed f
JOIN system.billing.usage u
  ON  u.workspace_id = f.workspace_id
  AND u.usage_metadata.job_run_id = f.run_id
  AND u.usage_date >= current_date() - INTERVAL 91 DAYS
JOIN system.billing.list_prices p
  ON  u.sku_name = p.sku_name AND u.cloud = p.cloud
  AND u.usage_unit = p.usage_unit
  AND u.usage_start_time >= p.price_start_time
  AND (p.price_end_time IS NULL OR u.usage_start_time < p.price_end_time)
GROUP BY ALL
ORDER BY failed_cost DESC

runs keeps one final state per run, because the timeline table stores many rows for each run.
